# 팀 협업 가이드

팀은 총 4명으로 확정됐다. 프로그래머 1명이 코드를 담당하고 나머지 팀원 3명이 기획, 3D 아트, 애니메이션, 레벨 구성과 Unity 에셋 배치를 분담한다. 파일별 담당자와 세부 역할 배정은 팀 협의 사항이다.

## 브랜치와 PR 제안

- 작업 시작 전 `git status --short --branch`로 브랜치와 로컬 변경을 점검한다. 원격이 연결된 뒤에는 깨끗한 `main`에서 `git pull --ff-only`를 실행하고 `feature/<작업>`, `art/<작업>`, `level/<작업>`, `fix/<작업>` 같은 작업 브랜치를 만든다.
- 하나의 PR에는 하나의 작업을 담는다. 작업 목적, 변경 경로와 씬·프리팹 이름, 담당자, Unity 검증 결과, 인계 사항을 적는다. 필요하면 스크린샷과 기획 질문 ID를 첨부한다.
- 병합 전 변경 영역을 아는 팀원 1인에게 리뷰를 요청한다. 프로그래머가 코드 변경을 확인하고, 프로그래머가 작성한 PR은 다른 팀원이 Unity에서 작업 결과를 확인한다.
- 병합 전에 최신 `main`을 작업 브랜치에 반영하고 충돌을 해결한다. 작업물 변경이 남아 있으면 먼저 안전하게 보관하고, 같은 씬이나 프리팹의 충돌은 양쪽 작업자와 조율한다.

## 커밋 메시지와 PR 제목 규칙

- 모든 커밋 메시지와 PR 제목은 영어로 작성한다. 커밋 제목과 PR 제목 모두 Conventional Commits 형식인 `type: concise description`을 사용한다.
- 기본 유형은 `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `perf`, `build`, `ci`다. 팀 전용 유형 `art`, `anim`, `level`은 각각 아트, 애니메이션, 레벨 작업에 사용할 수 있다.
- 제목에 변경 대상과 내용을 구체적으로 적는다. 예시는 `art: update courtyard stone materials`, `anim: adjust landing recovery timing`, `level: relocate courtyard spawn point`다.
- 검토하고 되돌리기 쉽도록 관련 변경만 하나의 커밋으로 묶는다.
- PR 생성 전에 허용 유형, 콜론과 공백, 구체적인 영어 설명을 확인한 뒤 검증한 제목으로 PR을 연다.

## 기획 문서 관리

- 기획 초안 원본과 버전은 [기획 초안 목록](DESIGN_DECISIONS.md#기획-초안)에서 확인한다. 구현 명세는 사용자가 승인한 [결정 기록](DESIGN_DECISIONS.md)을 기준으로 삼는다.
- 초안 개정본을 받으면 이전 버전과 비교해 변경 내용과 코드·데이터·씬·에셋에 미치는 영향을 PR 또는 인계 문서에 남긴다. 승인된 결정과 충돌하는 내용은 [미확정 질문](OPEN_QUESTIONS.md)에 기록하고 원본 PDF는 사용자 승인 없이 수정하거나 삭제하지 않는다.

## 파일 소유권과 씬 협업 제안

| 실제 경로 | 용도 | 담당 제안 |
| --- | --- | --- |
| `Assets/_Game/Scripts/` | 게임 코드 | 프로그래머 |
| `Assets/_Game/Scenes/Dev/` | 기능 검증용 씬 | 씬별 작업자 |
| `Assets/_Game/Scenes/Levels/` | 플레이 레벨 씬 | 레벨 담당자 중 씬별 1인 |
| `Assets/_Game/Prefabs/` | 재사용 프리팹 | 프리팹별 지정 담당자 |
| `Assets/_Game/UI/` | UI 작업 파일 | UI 작업자와 프로그래머 |
| `Assets/_Game/Data/` | 게임 데이터 | 기획 담당자와 프로그래머 |
| `Assets/Scenes/SampleScene.unity` | 기존 템플릿 샘플 씬 | 수정이 필요할 때 작업자 협의 |

- 씬과 프리팹은 작업 전에 팀 채널이나 작업표에 경로, 작업자, 예상 종료 시점을 공유한다. 같은 파일은 한 번에 한 명이 편집한다. 병합과 인계가 끝나면 점유를 해제한다.
- 레벨에서 재사용할 오브젝트는 프리팹으로 관리한다. 배치 변경은 씬에서 하고, 원본에 영향을 주는 Apply는 담당자와 조율한다. 충돌은 Unity에서 양쪽 변경 의도와 GUID·참조를 검증한 후 해결한다.
- Unity에서 이동하거나 이름을 변경하고 해당 `.meta`를 함께 반영한다. 빈 폴더의 `.gitkeep`은 Git에 초기 경로를 남기기 위한 파일이다. 실제 에셋이 들어오면 담당자와 정리할 수 있다.

## Unity와 에셋 임포트

- 모든 팀원이 프로젝트에 기록된 Unity `6000.3.24f1`과 URP 설정을 사용한다. 버전, 패키지, 프로젝트 설정 변경은 팀과 사전에 조율한다.
- 임포트 전 단위, 축, 스케일과 필요한 텍스처·애니메이션 설정을 담당자와 확인한다. 임포트 후 모델, 머티리얼, 애니메이션과 프리팹 참조를 Unity에서 확인하고 원본과 `.meta`를 함께 검토한다.
- 아트 구조 제안은 `Assets/_Game/Art/` 아래 `Models/`, `Textures/`, `Materials/`, `Animations/`를 두는 방식이다. 프로젝트 밖에서 관리할 편집 원본과 Unity에 포함할 원본을 합의한 뒤 실제 폴더를 만든다.
- Git LFS는 FBX, BLEND, PSD, TGA, EXR, WAV에 적용된다. 각 팀원의 사용 환경에 Git LFS를 설정하고, 원격을 사용하기 전에 저장 용량과 전송량 한도 및 과금 방식을 확인한다. 대형 파일의 반복 수정과 중복 원본은 저장량을 늘릴 수 있으므로 임시 내보내기와 백업 파일은 추가하기 전에 검토한다.

## 작업물 인계 제안

PR 또는 팀 작업표에 파일 경로, 담당자, 관련 브랜치와 PR, Unity에서 확인할 씬과 재현 절차, 임포트 변경과 의존성, 남은 작업 및 질문 ID를 남긴다. 다음 작업자가 Unity에서 열어 참조와 배치를 확인한 뒤 소유권을 넘겨받는다.
